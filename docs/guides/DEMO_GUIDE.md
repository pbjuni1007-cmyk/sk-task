# SK-TASK 실제 화면 시연 순서

현재 화면 코드의 버튼 이름과 기존 검증 기록을 대조한 발표용 절차다. 이 문서를 작성하며 모든 흐름을 브라우저에서 다시 실행한 것은 아니다. 현재 클라인즈 114,000원·LG 169,000원, 무료배송인 모의 상품 자료를 기준으로 한다. 상품 자료를 변경하면 기대 금액도 다시 확인한다.

## 시연 전 준비

1. [프로젝트 README](../../README.md)에 따라 저장소 루트에서 앱을 실행하고 `http://127.0.0.1:8501/`을 연다.
2. AI 시연에는 프로젝트 `.env`의 유효한 OpenAI 키가 필요하다. 직접 입력·규정 계산·문서 생성 시연은 AI 호출 없이 가능하다.
3. 희망 사양은 이번 기본 시연에서 비워둔다. 상품 근거에 없는 사양을 넣으면 제출이 제한될 수 있다.
4. 기존 기록과 구분하도록 구매 목적에 `시연-정상`, `시연-예산초과` 등의 이름을 사용한다. 기존 DB를 삭제할 필요는 없다.
5. 왼쪽 **시연 설정 → 시연 프로필 · 인증 아님**에서 역할을 바꾼다.

| 프로필     | 역할        |
| ---------- | ----------- |
| employee_a | 요청 직원 A |
| employee_b | 요청 직원 B |
| buyer_a    | 구매 담당자 |
| manager_a  | 추가 승인자 |

실제 주문·결제·외부 전송은 하지 않는다. 제출·결재는 로컬 SQLite에 기록한다. 상품 출처는 [상품 자료](../reference/COUPANG_FIXTURES.md), 요청·응답 계약은 [공식 API 대조](../reference/COUPANG_API_CONTRACT_CHECK.md)를 참고한다. 공식 본문 대조는 완료했으며 실제 쿠팡 API 호출은 하지 않았다.

## 발표 순서

AI가 업무를 이어가는 모습은 시나리오 1, 확실한 버튼 기반 정상 흐름은 시나리오 2로 보여준다. 이후 예산 초과와 추가 승인을 보여주고, 시간이 남으면 입력 보완·사용자 분리·최근 수정 확인을 진행한다.

## 1. AI 검색 → 여러 턴 수정 → 제출 확인

설계 연결: TS-01-C001/C002, TS-04-C002, TS-05-C001, TS-06-C001.

1. `employee_a` → **구매요청 작성 → AI로 입력**.
2. **AI 요청**에 아래 문장을 입력하고 **AI에게 요청**을 누른다.

   > 업무용 모니터 3대, 배송비 포함 예산 60만원, 목적은 시연-정상 신입 개발자 장비 지급이야. 모니터 후보를 찾아줘.

3. 후보 검색 안내가 나오면 같은 AI 입력창에 다음 문장을 보낸다.

   > 클라인즈 상품을 선택하고 문서 3종 만들어줘. 제출은 하지마.

4. 같은 화면에서 이어서 보낸다.

   > 선택 상품과 목적은 그대로 두고 수량만 4대로 바꿔서 검토하고 문서 다시 만들어줘.

5. `제출해줘`를 보낸다. 확인 화면이 나타나면 총액 **456,000원**, 수량 **4대**를 확인한다. 펼침 영역에서 문서 내용도 확인할 수 있다.
6. **AI 제출 취소**를 누른다. 제출 취소 안내를 확인한다.
7. 다시 `제출해줘` → **확인 후 제출**을 누른다.
8. **AI가 작업한 요청 열기** → **구매요청서 / 상품 비교표 / 규정 검토** 탭을 차례로 확인한다. 요청번호·버전·수량·단가·총액이 일치해야 한다.
9. 아래 공통 결재 절차로 구매 담당자 승인을 진행한다.

기대 결과: 검색만 요청했을 때 문서나 제출까지 진행하지 않는다. 수량 3대의 계산 금액은 342,000원이며 4대로 수정하면 456,000원이다. 목적과 선택 상품을 유지하고 사용자 확인 후에만 제출한다. AI의 자연어 응답 문구는 달라질 수 있으므로 저장된 문서와 상태를 기준으로 판정한다.

**AI 대화 화면을 떠나는 시점에 주의한다.** `AI가 작업한 요청 열기`로 이동한 상세 화면에는 AI 입력창이 없다. 여러 턴 수정과 AI 제출 확인을 먼저 끝낸 뒤 상세 화면을 연다. 사이드바의 `구매요청 작성`은 기존 대화로 복귀하는 버튼이 아니라 새 요청·새 대화를 시작하는 버튼이다.

## 2. 직접 입력 정상 구매 → 구매팀 승인

설계 연결: TS-04-C002, TS-10-C005. AI 호출 없이 같은 업무 서비스를 시연하는 경로다.

1. `employee_a` → **구매요청 작성 → 직접 입력**.
2. 수량 `3`, 예산 `600000`, 구매 목적 `시연-직접입력`, 희망 사양 비움.
3. **저장하고 상품 찾기**를 누른다.
4. 상품 카드의 가격·판매자·배송비를 확인한다. **쿠팡 상품 보기**를 눌러 실제 상품 페이지를 열 수 있다. 쿠팡 화면의 현재 가격과 모의 자료의 과거 가격은 다를 수 있다.
5. **구매 상품 선택**에서 클라인즈 → **선택 상품 적용 → 문서 만들기 →**.
6. **배송비 포함 총액 342,000원**과 문서 3개 탭을 확인한다.
7. **구매요청 제출 확인 → 제출**.
8. 아래 공통 결재 절차를 수행한다. 최종 상태는 **승인 완료**다.

### 공통 결재 절차

1. `buyer_a`로 변경 → **결재대기함**.
2. 대상 요청의 **열기**. 요청이 많으면 **요청번호 또는 제목**에 구매 목적이나 요청번호를 입력하고 **조회**한다.
3. **처리 종류 → 승인 → 처리 내용 확인 → 확인하여 처리**.
4. 일반 요청은 **승인 완료**, 100만원 이상 요청은 **추가 결재 대기**가 된다.

문서별 **다운로드** 버튼도 사용할 수 있다. 발표 PC에서 파일 저장 성공은 따로 확인한다. 기존 브라우저 검증에서는 버튼 클릭과 문서 내용까지 확인했고 실제 파일 저장 완료는 미확인이었다.

## 3. 예산 초과 → 조건 보완 → 이전 버전 확인

1. `employee_a` → **구매요청 작성 → 직접 입력**.
2. 수량 `4`, 예산 `400000`, 목적 `시연-예산초과`, 희망 사양 비움.
3. **저장하고 상품 찾기 → 구매 상품 선택: 클라인즈 → 선택 상품 적용 → 문서 만들기 →**.
4. 총액 **456,000원**과 예산 초과 안내를 확인한다. 초과액은 **56,000원**이며 **구매요청 제출 확인**은 비활성화되어야 한다.
5. **구매 조건 보완** → 예산 `500000` → **구매 조건 저장 → 문서 만들기 →**.
6. 새 버전에서 제출 가능 상태인지 확인한다.
7. **요청 정보 · 이전 버전 → 조회 버전**에서 변경 전 버전을 선택한다. 이전 초안이 보존되고 읽기 전용으로 표시되어야 한다. 이후 최신 버전을 다시 선택한다.

이 사례는 예산 초과·버전 보존의 화면 시연이다. 정확히 499,999원/500,000원인 비교 규정 경계 테스트를 대신하지 않는다.

## 4. 100만원 이상 → 추가 승인

1. `employee_a` → 직접 입력으로 수량 `6`, 예산 `1100000`, 목적 `시연-추가승인`.
2. **저장하고 상품 찾기**. 검색어는 `모니터`를 유지해 두 후보를 확보한다.
3. **구매 상품 선택: LG 27MS500 → 선택 상품 적용 → 문서 만들기 →**.
4. 총액 **1,014,000원** 확인 → **구매요청 제출 확인 → 제출**.
5. `buyer_a` → **결재대기함 → 대상 요청 열기 → 승인 → 처리 내용 확인 → 확인하여 처리**.
6. **추가 결재 대기**를 확인한다.
7. `manager_a` → **결재대기함 → 대상 요청 열기 → 승인 → 처리 내용 확인 → 확인하여 처리**.
8. **승인 완료**를 확인한다.

구매 담당자 승인만으로 완료되면 안 된다. 정확히 999,999원/1,000,000원인 TS-09-C002 경계는 자동 테스트로 설명한다.

## 5. 입력 부족·지원 범위·사용자 분리

각 새 AI 요청은 **구매요청 작성 → AI로 입력**에서 시작한다.

| 항목           | 조작                                                                            | 기대 결과                     | 설계 연결                   |
| -------------- | ------------------------------------------------------------------------------- | ----------------------------- | --------------------------- |
| 수량·예산 없음 | AI에 `모니터 구매요청서 써줘`                                                   | 조건 보완 안내                | TS-07-C001                  |
| 지원 범위 밖   | AI에 `점심 메뉴 추천해줘`                                                       | 모니터 구매 지원 범위 안내    | TS-07-C004                  |
| 목적 없이 초안 | 직접 입력: 수량 3, 예산 600000, 목적 비움 → 클라인즈 선택 → 문서 생성           | 초안은 있고 제출은 차단       | TS-07-C005                  |
| 목적 보완      | 위 요청에서 **구매 조건 보완** → 목적 입력 → **구매 조건 저장 → 문서 만들기 →** | 새 버전에서 제출 가능         | 목적 누락 후 보완           |
| 사용자 분리    | A로 만든 요청번호를 기록 → `employee_b` → **내 요청함** → 해당 번호로 **조회**  | A의 요청이 목록에 보이지 않음 | TS-05-C002의 목록 격리 부분 |

프로필 전환은 시연용이다. 이 화면만으로 운영 로그인 보안을 검증했다고 설명하지 않는다.

## 6. 반려·보완 요청

1. 직원이 별도 요청을 제출한다.
2. `buyer_a` → **결재대기함 → 열기**.
3. **처리 종류**에서 **반려** 또는 **보완 요청**을 선택한다.
4. **처리 의견 · 반려 / 보완 요청 시 필수**를 비워두면 **처리 내용 확인**이 비활성화되는지 확인한다.
5. 사유 입력 → **처리 내용 확인 → 확인하여 처리**.
6. 보완 요청을 선택했다면 `employee_a` → **보완요청함 → 열기 → 구매 조건 보완**으로 수정하고 문서를 다시 생성·제출한다.

## 7. 최근 PR 수정 확인

| 수정                              | 화면 조작                                           | 판정 범위                                |
| --------------------------------- | --------------------------------------------------- | ---------------------------------------- |
| PR #3: 새 요청의 AI 상태 초기화   | AI 대화를 한 뒤 **구매요청 작성 → AI로 입력**       | 이전 대화와 제출 확인이 남지 않아야 함   |
| PR #4: 변경 없는 재검토 문서 보존 | 제출 전 문서 생성 → **← 상품 선택 → 문서 만들기 →** | 같은 조건·버전으로 문서 화면에 정상 도달 |

PR #4의 버튼은 검토 후 문서를 다시 생성하므로, 버튼 흐름만으로 내부 검토 직후의 bundle ID 보존을 입증할 수 없다. 그 조건은 `test_repeat_review_preserves_ready_documents` 자동 테스트로 확인한다.

## 일반 화면 시연과 테스트의 구분

설계 38개를 모두 클릭만으로 재현할 수 있는 것은 아니다. 과거 브라우저 검증은 일반 화면 14개·오류 주입 20개·QA 콘솔 4개로 구분했다. 위 발표 절차가 그 38개 전체 또는 일반 화면 14개 전체를 다시 수행했다는 뜻은 아니다.

| 별도 확인 항목                                                       | 확인 방법                                                |
| -------------------------------------------------------------------- | -------------------------------------------------------- |
| API 500·403·429·timeout, 가격 누락, 빈 후보, 허위 응답·상품명 지시문 | 자동 테스트 및 당시 오류 주입 기록                       |
| 정확한 금액 경계, 유료배송 계산, 상품 가격 변경                      | 합성 자료를 사용하는 자동 테스트                         |
| 문서 부분 생성 실패, 반복 호출 한도, 대화 요약                       | 결정적 모델·오류 주입 테스트                             |
| 동일 토큰 중복 제출, 잘못된 API 인자, link-only 응답                 | 서비스/API 테스트 및 당시 QA 콘솔 기록                   |
| 실제 모델 성능 20회·사용자 선호 저장과 재사용 등                     | 별도 평가와 기존 관찰 기록. 위 기본 발표 절차에서는 생략 |

[테스트 추적표](../validation/TEST_TRACEABILITY.md)에서 케이스별 코드를, [브라우저 검증 보고서](../validation/BROWSER_QA_REPORT.md)에서 실제 수행 범위를 확인한다. 오류 주입용 `runtime/browser-qa/`는 Git 제외 대상이라 저장소를 새로 받은 뒤 그대로 실행할 수 있는 공개 시연 도구는 아니다. 검사 및 실제 모델 평가 명령은 [개발 안내](DEVELOPMENT.md)에 있다.
